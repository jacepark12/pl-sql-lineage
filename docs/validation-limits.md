# 검증의 한계 — 합성 코퍼스가 말해주지 않는 것

엔진의 모든 수치는 합성 코퍼스에서 나왔습니다. 그 수치가 **무엇을 보장하고 무엇을 보장하지
않는지**를 적어 둡니다. 측정 방법 자체는 [engine-architecture.md](engine-architecture.md)에,
현재 점수는 [engine-roadmap.md](engine-roadmap.md)에 있습니다.

## 보장되는 것 — 라벨의 정확성

정답셋은 엔진과 무관하게 만들어집니다. 생성기가 같은 중간표현에서 SQL 텍스트와 리니지 정답을
**동시에** 파생시키므로, 정답이 엔진의 편향을 물려받을 수 없고 라벨링 오류가 섞일 여지도
없습니다. 흔한 대안 — 기존 파서로 코퍼스를 라벨링하는 것 — 은 순환이고, 그 파서의 버그가
그대로 정답의 버그가 됩니다.

따라서 "정답이 틀렸을 수도 있다"는 걱정은 하지 않아도 됩니다. **내적 타당도는 강합니다.**

## 보장되지 않는 것 — 실무 코드에서의 일반화

합성 코퍼스는 렌더러가 찍어냅니다. 구문 **분포**는 실제 자산을 본떴지만 **표기**는 균일합니다.
30만 라인을 실측한 결과입니다.

| 항목 | 합성 코퍼스 | 실무 코드에서 기대되는 것 |
|---|---|---|
| 키워드 대소문자 | `SELECT` `FROM` `WHERE` 전부 대문자, 소문자·혼용 **0건** | 파일마다 제각각 |
| 들여쓰기 | 4·6·11·2·20 칸에 집중 | 탭/스페이스 혼용, 정렬 규칙 불일치 |
| 라인 길이 | 중앙값 32, p95 52 | 수백 자 한 줄 흔함 |
| 주석 | `--` 30,994건 / 블록주석 **0건**(`/*+ 힌트 */` 270건이 전부) | `/* */` 블록주석 일상적 |
| `q'[...]'` 대체 인용 | **0건** | 문자열에 따옴표가 들어갈 때 사용 |
| 인용 식별자 `"Col"` | **0건** | 대소문자 구분이 필요한 레거시에서 사용 |
| 중첩 서브프로그램 | **0건** | 프로시저 안의 프로시저 |
| `GOTO` / `<<label>>` | **0건** | 레거시 배치에 잔존 |
| `PIPELINED` / `AUTHID` / `DETERMINISTIC` | **0건** | 실무에서 사용 |

**`q'[...]'` 가 0건인 것이 특히 중요합니다.** A 계층으로 직접 스캐너 대신 ANTLR 을 고른
이유가 바로 주석·리터럴 마스킹의 취약점이었는데, 그 취약점을 시험할 입력이 코퍼스에
하나도 없습니다. 지금의 100% 는 그 위험이 없다는 뜻이 아니라 **시험되지 않았다는
뜻**입니다.

ANTLR 문법(grammars-v4)은 실제 Oracle 을 보고 쓰인 것이라 위 항목 대부분을 이미 알고 있을
것으로 기대됩니다. 다만 **기대일 뿐 확인된 바 없습니다.** 확인은 실무 코드를 넣어봐야만
됩니다.

## 실무 코드로 무엇을 잴 수 있나

정답셋이 없으므로 P/R/F1 은 계산할 수 없습니다. 그래도 다음은 정답 없이 측정됩니다.

| 측정 항목 | 방법 | 무엇을 알려주나 |
|---|---|---|
| **파싱 성공률** | `result.problems` 가 빈 파일 비율 | A 계층이 실무 표기를 견디는가 |
| **구문 오류 위치 분포** | 실패한 파일의 첫 오류 줄을 모아 유형화 | 문법의 어느 규칙이 부족한가 |
| **미분석 문장 비율** | `SQL_NOT_ANALYZED` 진단 수 / 전체 DML | B 계층이 못 읽는 구문의 실제 빈도 |
| **미해결 이름 비율** | `Edge.unresolved` 가 남은 엣지 비율 | C 계층이 못 잇는 흐름의 빈도 |
| **엣지 밀도** | 1천 라인당 엣지 수를 합성 코퍼스와 비교 | 조용한 대량 누락의 신호 |
| **처리량** | 라인/초 | 30만 라인 추정치의 검증 |

앞의 셋이 가장 값집니다. **파싱 실패와 미분석 진단은 정답이 없어도 그 자체로 결함**이기
때문입니다. 반대로 "엣지가 나왔다"는 것은 정답 없이는 맞았다는 증거가 되지 못합니다.

엔진은 이미 이 셋을 전부 냅니다. 파싱 실패는 `PARSE_FAILED`, 미분석 문장은
`SQL_NOT_ANALYZED` 진단으로 나오고, 둘 다 파일·패키지·프로시저·줄 위치를 함께 기록합니다.

```sh
python3 -m plsqllineage.engine --input <실무코드경로> --out real.json
python3 -c "
import json, collections
d = json.load(open('real.json'))
print(collections.Counter(x['code'] for x in d['diagnostics']))
print(collections.Counter(x['message'] for x in d['diagnostics']).most_common(10))"
```

## 실무 코드를 다루는 규약

이 저장소에는 **운영 SQL 을 커밋하지 않습니다.** 이전에 `fixtures/private/` 에 있던 규약을
그대로 따릅니다(디렉터리는 커밋 `9dff998` 에서 제거되었지만 규약은 유효합니다).

- 원본 운영 SQL 을 저장하지 않습니다.
- 스키마·테이블·컬럼·패키지·프로시저·리터럴·주석 내용을 결정적 가명으로 치환합니다.
- **의존 형태, 문장 순서, PL/SQL 제어 구조는 보존합니다.** 익명화가 표기 다양성까지
  지워버리면 이 검증의 목적이 사라집니다.
- 공개 배포에서 제외합니다.

익명화 자체가 위험을 안고 있다는 점은 짚어 둘 필요가 있습니다. 이름을 규칙적인 가명으로
바꾸면 **길이·대소문자·인용 여부가 균일해져** 지금 문제 삼는 그 균일함이 다시 생깁니다.
치환 규칙은 원본의 표기 특성을 보존하도록 만들어야 합니다.

민감도가 높아 익명화조차 어렵다면, 파일을 저장소 밖에 두고 **진단 통계만** 가져오는 것으로도
위 여섯 항목 중 다섯은 측정됩니다.

## 그래서 지금 수치를 어떻게 읽어야 하나

Tier 0~1 의 100% 와 Tier 3 의 F1 78.6% 는 **"이 구문 분포에서 이 정도 정확도"** 이지
**"실무 코드에서 이 정도"** 가 아닙니다. 두 번째 주장을 하려면 최소한 파싱 성공률과
미분석 비율을 실무 코드에서 재야 하고, 정확도까지 주장하려면 익명화 표본에 사람이 라벨을
붙인 소규모 정답셋이 필요합니다.

우선순위는 [engine-roadmap.md](engine-roadmap.md)에 있습니다. 실무 코드 검증은 그 목록의
어느 항목보다 **싸고**(파싱만 돌리면 됨) **불확실성이 큽니다**(무엇이 나올지 모름).
표본을 구할 수 있게 되는 즉시 하는 것이 합리적입니다.
