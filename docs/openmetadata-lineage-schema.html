01The unit typetype/entityLineage.json

All column lineage is one type, three fields

There is no column-lineage entity, no column-lineage table, and no column-lineage endpoint. The entire vocabulary is a single definition nested inside the table-to-table edge that owns it.

definitions.columnLineage → org.openmetadata.schema.type.ColumnLineage

fromColumns : array<fullyQualifiedEntityName>   // N source columns
toColumn    : fullyQualifiedEntityName          // 1 target column
function    : sqlFunction                       // optional

Columns are not entities in OpenMetadata — they are sub-fields of a table entity, so they have no UUID. Every reference above is a plain string. That string length cap is the only format constraint the schema imposes on column lineage.

02Containmentfigure 1

How a column mapping is reached

Containment runs one way. To read or write a single column mapping you descend the whole chain from the edge; there is no path in the other direction, and no constraint binds the strings inside ColumnLineage to the columns they name.

Read the sqlFunction description carefully

function was designed to hold a function name, not an expression. One connector in the entire codebase populates it — the SAP HANA calculation-view parser. Every SQL-parsing path leaves it null, and the ingestion client's merge routine discards it outright.

Two shapes worth noting

SearchLineageResult returns maps rather than arrays — nodes keyed by FQN, edges keyed by document id — using existingJavaType to bypass generation. And NodeInformation.entity is typed as Map<String, Object>: node bodies are passed through untyped rather than modeled as a union of twenty-odd entity types.

EsLineageData re-uses the identical columnLineage definition by $ref, so storage and index share one generated type. It differs from the core edge in two deliberate ways: endpoints are a lightweight relationshipRef carrying fqnHash, and repeated SQL is replaced by a sqlQueryKey pointing into a map on the parent document.

07Consequencefigure 3

What the shape costs an agent writer

Because column mappings live inside a blob that is replaced wholesale, and because the write API accepts no partial update, a caller that omits lineageDetails does not leave the existing mappings alone — it erases them. OpenMetadata's own MCP tool takes exactly this path.

08Absencesassessment

What the schema does not model

Each of these is a field that does not exist anywhere in the lineage types. Several exist elsewhere in the OpenMetadata spec — confidence is defined for classification and recognizers, and a review workflow exists for descriptions and tags — but neither was extended to lineage.

MissingStatusWhat it would answer

The absence that compounds

Mappings that cannot be resolved are dropped at two layers — the ingestion client discards a pair when either FQN fails to resolve, and the server filters any mapping naming a column that does not exist, logging at debug and returning no warning.

The result is that absence is unfalsifiable. A consumer reading this schema cannot tell an empty columnsLineage caused by "these tables genuinely share no columns" from one caused by "the parser timed out" or "the catalog had not ingested the columns yet." For a system that answers impact questions, that is the most expensive gap on the list.
