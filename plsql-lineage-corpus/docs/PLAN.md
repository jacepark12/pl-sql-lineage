# 합성 PL/SQL 코퍼스 생성기 기획서

**문서 목적** — 컬럼 레벨 리니지(Column-level Lineage) 파서 및 엔진 개발·검증에 사용할
합성(synthetic) PL/SQL 코퍼스 생성기의 설계와 구축 계획을 정의한다.

| 항목 | 내용 |
|---|---|
| 작성일 | 2026-08-12 |
| 대상 시스템 | 레거시 Oracle PL/SQL 기반 WMS 계열 |
| 산출물 | 합성 코퍼스 생성기 + 코퍼스 + 리니지 정답셋 |
| 저장 위치 | `plsql-lineage-corpus/` |

구현 상태와 실행 방법은 [../README.md](../README.md)를 참고한다. 이 문서는 설계 근거를
남기는 용도이며, 구현 과정에서 기획과 달라진 부분은 마지막 장에 정리했다.

---

## 1. 배경

컬럼 레벨 리니지 엔진을 개발하려면 대량의 PL/SQL 샘플이 필요하다. 그러나 실제 운영
시스템의 소스는 테스트 자산으로 사용할 수 없다.

- **법적/계약적 제약** — 운영 코드는 고객사 자산이며 외부 반출·공개 저장소 커밋 불가
- **업무 정보 노출** — 테이블/컬럼명, 코드값, 분기 조건 자체가 업무 로직을 드러냄
- **CI 활용 불가** — 회귀 테스트 픽스처로 레포에 상주시킬 수 없음
- **정답 부재** — 운영 코드에는 "이 컬럼이 어디서 왔는가"에 대한 정답 레이블이 없어,
  수작업 라벨링 없이는 엔진 정확도를 측정할 수 없음

따라서 **구조적 난이도는 실제 코드와 동등하되, 업무 내용은 완전히 가상인 코퍼스**를
직접 생성한다.

### 1.1 실측 기반 설계

생성기의 사양은 임의로 정하지 않고, 실제 레거시 PL/SQL 자산 **390개 패키지 /
612,825 라인**을 정적 분석해 얻은 구문 출현 통계를 기준으로 삼는다.

> 이때 코퍼스에 반영되는 것은 **"CASE WHEN이 1,000라인당 12.7회 출현한다"는 통계값**이며,
> 실제 코드 문자열·식별자·업무 로직은 일절 이식하지 않는다. 통계는 코드가 아니므로
> 반출 제약에 걸리지 않으면서, 파서가 마주칠 난이도는 그대로 재현할 수 있다.

## 2. 핵심 설계 원칙

### 원칙 1. 정답에서 코드를 역생성한다 (Generate-from-Truth)

일반적인 접근은 코드를 만든 뒤 정답을 라벨링하는 것이다. 이 방식은 라벨링 비용이
코퍼스 규모에 비례해 증가하고, 라벨 자체에 오류가 섞인다.

본 생성기는 **반대 방향**으로 동작한다.

```
리니지 그래프(IR)  ──렌더링──▶  PL/SQL 소스 텍스트
        │
        └────추출────▶  리니지 정답 JSON
```

동일한 중간표현(IR)에서 소스와 정답을 **동시에** 파생시키므로:

- 정답이 항상 100% 정확하다 (라벨링 오류 원천 차단)
- 코퍼스를 100만 라인으로 늘려도 라벨링 추가 비용이 0이다
- 정답을 먼저 설계할 수 있다 — "3홉 리니지 + CASE 분기 + 집계" 같은 특정 난이도를
  의도적으로 주문 생산할 수 있다

이것이 합성 코퍼스를 택하는 가장 큰 실익이다. 제약을 우회하는 차선책이 아니라,
정답셋 확보 측면에서 실제 코드보다 우월하다.

### 원칙 2. 구조적 충실도 > 의미적 충실도

생성된 코드가 "그럴듯한 업무 로직"일 필요는 없다. 파서 관점에서 중요한 것은
문법 구조와 참조 관계뿐이다. 다음은 반드시 재현한다:

- 복합 PK(창고+전표+라인) 기반 다중 컬럼 조인
- 동일 컬럼명이 여러 테이블에 반복 등장 (alias 해석 강제)
- 500라인급 대형 프로시저, 40,000라인급 초대형 패키지
- 한글 주석 및 한글 리터럴 (멀티바이트 처리 검증)
- 오라클 구식 조인 `(+)`, 힌트 주석 `/*+ ... */`

### 원칙 3. 재현 가능성

동일 seed → 동일 코퍼스. CI에서 회귀 테스트로 쓰려면 필수다.

### 원칙 4. 난이도 계층화

전량이 어려우면 개발 초기에 진척도를 볼 수 없고, 전량이 쉬우면 실전에서 무너진다.
Tier 0~3으로 나누어 점진적 개발을 지원한다.

## 5. 상세 설계

### 5.1 가상 스키마

3개 스키마로 분리해 실제 레거시의 스키마 간 참조 구조를 재현한다.

| 스키마 | 역할 | 주요 테이블 |
|---|---|---|
| `SYNWMS` | 업무 | 기준정보, 입고, 재고, 출고, 집계 |
| `SYNIF` | 인터페이스 | 수신/송신 테이블 |
| `SYNARC` | 아카이브 | 이력 보관, 작업 로그 |

**의도된 다단 리니지 체인** — 리니지 엔진의 핵심 시험대는 단일 문장이 아니라 다중 홉이다.

```
IF_ITEM_RCV ──▶ MST_ITEM ──┐
                            ├─▶ INB_RESULT ─▶ STK_ONHAND ─▶ STK_TRX ─▶ RPT_DAILY_STK
INB_ORDER_H/D ──────────────┘                     │
                                                  └─▶ OUT_ALLOC ─▶ OUT_PICK ─▶ OUT_SHIP ─▶ IF_ORDER_SND
```

최장 6홉. 엔진이 `RPT_DAILY_STK.END_WGT`에서 역추적해 `SYNIF.IF_ITEM_RCV.UNIT_WGT`까지
도달하는지가 최종 검증 항목이 된다.

### 5.2 중간표현(IR) 모델

표현식을 완전한 AST로 모델링하면 구현 비용이 크다. **템플릿 + 참조 목록** 방식을
채택한다 — 렌더링과 리니지 추출 양쪽에 정확하면서 코드량이 훨씬 작다.

```python
@dataclass
class Expr:
    template:  str        # "NVL({0}, 0) * {1}"
    refs:      tuple[Ref] # [ColRef(STK_ONHAND, ONHAND_QTY), Var(v_rate)]
    kind:      str        # DIRECT | TRANSFORM | AGGREGATE | ANALYTIC
    cond_refs: tuple[Ref] # CASE 조건절 참조 → INDIRECT_FILTER
```

- **렌더링** = `template.format(*[r.sql() for r in refs + cond_refs])`
- **리니지** = `refs` 를 kind와 함께 수집, `cond_refs` 는 INDIRECT_FILTER로 분리

참조 타입:

| 타입 | 설명 |
|---|---|
| `ColRef(table, column, alias)` | 테이블 컬럼 참조 |
| `Var(name)` | PL/SQL 변수 — 바인딩 맵으로 원천 컬럼에 해석 |
| `Star(table, alias)` | `a.*` — 카탈로그로 전개 |
| `ScalarSubquery(select)` | 상관 스칼라 서브쿼리 |
| `Lit(text)` | 리터럴 |

문장 타입: `InsertSelect`, `InsertValues`, `Update`, `Merge`, `SelectInto`,
`CursorLoop`, `OpenRefCursor`, `ExecImmediate`, `Delete`, `Assign`, `ForAll`,
`ForLoop`, `IfBlock`, `Raw`

### 5.3 리니지 엣지 분류

단순 "연결됨"이 아니라 관계의 성격을 구분해야 실용적인 엔진이 된다.

| 엣지 종류 | 발생 위치 | 예 |
|---|---|---|
| `DIRECT` | 단순 컬럼 대입 | `INSERT ... SELECT a.ITEM_CD` |
| `TRANSFORM` | 함수/연산 경유 | `NVL(a.RCV_QTY,0) * b.UNIT_WGT` |
| `AGGREGATE` | 집계함수 | `SUM(a.TRX_QTY)` |
| `ANALYTIC` | 분석함수 PARTITION/ORDER | `ROW_NUMBER() OVER(PARTITION BY ...)` |
| `INDIRECT_FILTER` | WHERE / JOIN / CASE 조건절 | `WHERE a.STAT_CD = '10'` |
| `VIA_VARIABLE` | PL/SQL 변수 경유 | `SELECT INTO v_qty` → `VALUES(v_qty)` |
| `VIA_CTE` | CTE 경유 (전이 해석 필요) | `WITH t AS (...) SELECT t.QTY` |
| `UNRESOLVED` | 동적 SQL | `EXECUTE IMMEDIATE v_sql` |

`INDIRECT_FILTER`를 별도 분류하는 이유 — 실무에서 "이 컬럼이 바뀌면 무엇이 영향받나"를
물을 때 필터 컬럼도 답에 포함되어야 하지만, "이 값이 어디서 왔나"를 물을 때는
제외되어야 한다. 두 질의를 구분하려면 생성 시점부터 분리 라벨링이 필요하다.

`via` 속성은 값이 거쳐 온 경로를 별도로 기록한다 — `CTE`, `VARIABLE`,
`DERIVED`(`MERGE ... USING` 투영). 표현식 종류(kind)와 전달 경로(via)를 분리하면
`SUM()`이 CTE를 거친 경우처럼 두 성질이 겹칠 때도 정보를 잃지 않는다.

### 5.4 정답 파일 포맷

```json
{
  "corpus_version": "1.0",
  "seed": 20260812,
  "edges": [
    {
      "target": { "table": "SYNWMS.STK_ONHAND", "column": "ONHAND_QTY" },
      "sources": [ { "table": "SYNWMS.INB_RESULT", "column": "RCV_QTY" } ],
      "kind": "TRANSFORM",
      "transform": "NVL(r.RCV_QTY, 0)",
      "hops": 1,
      "location": {
        "file": "packages/SYNWMS.PKG_IN_RECEIPT.sql",
        "package": "PKG_IN_RECEIPT",
        "procedure": "SP_APPLY_RECEIPT",
        "line": 128
      }
    }
  ],
  "ref_cursors": []
}
```

`location.line`을 포함하는 이유 — 엔진이 틀렸을 때 어느 문장에서 틀렸는지 즉시
역추적 가능해야 디버깅 사이클이 돈다. SELECT 항목 엣지는 그 항목 줄을, 필터 엣지는
그 술어 줄을 가리킨다.

### 5.5 난이도 티어

| Tier | 포함 구문 | 비중 | 용도 |
|---|---|---:|---|
| **0** | 단순 `INSERT ... SELECT`, 단일 테이블, 컬럼 1:1 | 15% | 파서 스모크 테스트 |
| **1** | 다중 조인, `CASE`/`DECODE`, `NVL`, 명시적 컬럼목록 | 40% | 기본 정확도 측정 |
| **2** | `MERGE`, CTE, 집계/분석함수, `SELECT *`, `(+)` 조인, 변수 매개 | 35% | 실전 수준 |
| **3** | 커서 루프, `BULK COLLECT`, REF CURSOR, `CONNECT BY`, `PIVOT`, 동적 SQL, 초대형 패키지 | 10% | 한계 시험 |

각 패키지는 단일 Tier로 태깅되어 `manifest.json`에 기록된다. 개발 초기에는
`--tier 0,1`만 생성해 빠르게 반복하고, 이후 확장한다.

### 5.6 평가 지표

생성기와 함께 채점기(`score.py`)를 제공한다. 엔진 출력과 정답을 대조해 산출:

| 지표 | 정의 |
|---|---|
| 파싱 성공률 | 문법 오류 없이 파싱된 파일 비율 |
| 엣지 Precision | 엔진이 낸 엣지 중 정답에 있는 비율 |
| 엣지 Recall | 정답 엣지 중 엔진이 찾은 비율 |
| 엣지 F1 | 위 둘의 조화평균 |
| Kind 정확도 | 엣지를 찾았을 때 종류(DIRECT/INDIRECT 등)까지 맞춘 비율 |
| Tier별 F1 | 난이도별 분해 — 어디서 무너지는지 파악 |
| 다홉 정확도 | 2홉 이상 리니지 체인 완주 비율 |

**UNRESOLVED 처리 규칙** — 동적 SQL 구간은 커버리지 지표에서 분리 집계한다.
정적 해석이 원리적으로 불가능한 영역을 억지로 추적하려다 엔진 전체 복잡도가
폭증하는 것을 막기 위해, 처음부터 "해석 불가"를 정상 출력으로 인정한다.

## 8. 기획 대비 변경 사항

구현하면서 기획을 바꾼 지점과 이유를 남긴다.

1. **구문 쿼터를 자기 조정식으로** — 시나리오를 균등 확률로 뽑으면 실측 분포를 맞출 수
   없었다. 각 구문의 남은 할당량에 비례해 시나리오를 뽑고, 모든 할당량이 소진되면
   DML 없는 순수 제어흐름 프로시저를 만든다. 실측 DML 비율(1K라인당 1.5~1.9회)이 낮아,
   "DML을 만들지 않는 선택지"가 없으면 어떤 가중치를 줘도 초과 생성된다.

2. **티어 배분을 패키지 개수가 아닌 라인 수 기준으로** — 개수로 나누면 특정 티어가
   작은 패키지에만 몰려 실제 라인 비중이 선언값과 크게 어긋난다. 30개 패키지 실험에서
   Tier 3가 한 개도 생성되지 않는 경우도 있었다.

3. **`via` 속성 추가** — 기획의 `VIA_CTE` / `VIA_VARIABLE`은 kind 하나에 표현식 종류와
   전달 경로를 겹쳐 담는다. `SUM()`이 CTE를 거치면 둘 중 하나를 버려야 해서, 경로를
   `via`로 분리했다. kind는 표현식 성격을, via는 전달 경로를 나타낸다.

4. **`DERIVED` 전달 경로 추가** — `MERGE ... USING` 투영은 CTE와 달리 리니지 홉이
   아니지만, 바깥 표현식에는 원천 컬럼명이 나타나지 않는다. 홉으로 세지 않으면서
   그 사실만 기록하기 위해 별도 경로로 뒀다.

5. **한 문장이 여러 구문을 동시에 나르게 함** — 구문마다 전용 INSERT 문을 두면
   실측 INSERT 비율(1K라인당 1.52회)로는 감당이 안 된다. CTE·GROUP BY·분석함수·`(+)`
   조인의 할당량 합만으로 이미 INSERT 할당량을 넘긴다. 실제 코드가 그렇듯 하나의
   `INSERT ... SELECT` 가 여러 구문을 함께 담도록 `sc_insert_join` 을 공용 캐리어로
   만들어 해결했다. 처음에는 이 문제를 인지하지 못해 `AGGREGATE` 엣지가 아예
   생성되지 않았다 (집계가 CTE 안에만 있어 전부 `VIA_CTE` 로 승격됨).

6. **`stmt_id` 필드 제외** — 기획의 정답 포맷에는 `location.stmt_id`가 있었으나,
   문장 번호는 생성기 내부 카운터이고 엔진이 대조할 수 없는 값이라 뺐다. 대신
   `line`을 술어 단위까지 정밀하게 맞췄다.

## 9. 향후 확장

- **MyBatis `.sqlx` 합성** — 실제 시스템의 리니지는 PL/SQL에서 끝나지 않는다.
  MyBatis 매퍼(동적 태그 `<if>`/`<foreach>` 포함) 합성 생성기를 추가해
  애플리케이션 계층까지 리니지를 잇는다. 동적 태그는 PL/SQL 동적 SQL보다
  구조가 명시적이라 오히려 해석 난도가 낮다.
- **오답 주입(mutation)** — 정답 엣지를 의도적으로 비틀어 채점기가 오류를
  잡아내는지 검증하는 메타 테스트. `score.py`의 열화 시나리오 테스트가 초기 형태다.
- **공개 벤치마크화** — 합성 데이터이므로 외부 공개에 제약이 없다. 컬럼 리니지
  분야에 표준 벤치마크가 부재하므로 공개 자산으로 전환 가능하다.
