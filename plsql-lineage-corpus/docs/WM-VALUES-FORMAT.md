# webMethods `Values` 바이너리 포맷 — 관측 사실과 가정의 분리

`IRTNODE_PROPERTY` 에 base64로 담긴 어댑터 메타데이터의 인코딩 명세다.
`syneai/wmvalues.py` 가 이 문서를 구현한다.

> **이 문서에서 가장 중요한 것은 아래 표의 "근거" 열이다.**
> 실제 webMethods 디코더와의 바이트 호환은 **검증되지 않았다.** 관측 표본이
> base64 조각 1건(33바이트)뿐이기 때문이다. 관측된 부분과 규약으로 정한 부분을
> 섞어서 서술하지 않기 위해 문서를 따로 둔다.

---

## 1. 관측 사실

`docs/PLAN-EAI.md` 3장에 인용된 실제 블롭의 선두 조각:

```
CwQAAAABBQEEGQBjAG8AbQAuAHcAbQAuAGQAYQB0AGEA
```

base64 디코딩 결과 33바이트:

```
0B  04 00 00 00 01 05 01  04 19 00  63 00 6F 00 6D 00 2E 00 77 00 6D 00 2E 00 64 00 61 00 74 00 61 00
└┘  └───────────────────┘  └──────┘  └──────────────────────────────────────────────────────────────┘
버전?      전문(preamble)    문자열     "com.wm.data"  (UTF-16LE, 25자 중 11자에서 잘림)
                            태그+길이
```

확인된 것:

| 항목 | 값 | 근거 |
|---|---|---|
| 선두 8바이트 | `0B 04 00 00 00 01 05 01` | 관측 |
| 문자열 태그 | `0x04` | 관측 |
| 문자열 길이 필드 | `19 00` = 25, **uint16 리틀엔디안** | 관측 |
| 문자열 인코딩 | UTF-16LE | 관측 |
| 첫 문자열 값 | `com.wm.data.ISMemDataImpl` (25자) | 관측 (11자까지 확인, 길이 25와 일치) |

### 1.1 기획서 서술 정정

`PLAN-EAI.md` 3장은 길이 필드를 "2바이트(빅엔디안)"로 적었으나, 실제로는
**리틀엔디안**이다. `19 00` 을 빅엔디안으로 읽으면 0x1900 = 6400 이 되어
25자라는 관측과 맞지 않는다. 기획서 본문의 `04 19 00` → 25자 서술 자체는
리틀엔디안을 전제하고 있으므로, 표기만 잘못된 것으로 판단한다.

## 2. 관측되지 않은 부분

33바이트 안에는 **문자열 태그 하나만** 나타난다. 정수·불린·배열·중첩 레코드
태그는 한 번도 관측되지 않았다.

이것이 문제가 되는 이유 — 리니지에 실제로 필요한 값이 전부 배열이다.

| 키 | 타입 | 리니지 용도 |
|---|---|---|
| `tables.columnInfo` | 문자열 배열 (표본 39건) | 컬럼 카탈로그 |
| `update.column` | 문자열 배열 | 엣지 종점 |
| `update.inputField` | 문자열 배열 | 엣지 시점 |
| `update.expression` | 문자열 배열 | TRANSFORM / 상수 |
| `select.outputField` / `select.refColumn` | 문자열 배열 | Select 어댑터 엣지 |

즉 **관측된 정보만으로는 어댑터 메타데이터를 인코딩할 수 없다.**

---

## 3. 이 생성기가 채택한 규약

관측되지 않은 부분은 아래와 같이 **선언**한다. 관측 사실이 아니라 규약이다.

### 3.1 문서 구조

```
document := PREAMBLE(8) STRING(impl_class) record_body
record_body := u32le entry_count  (key, value) * entry_count
key   := STRING
value := tag(1) payload
```

`PREAMBLE` 은 관측된 8바이트를 그대로 쓴다. 각 바이트의 의미는 해석하지 않았다 —
버전·엔트리 수·인코딩 표시 중 무엇인지 판단할 근거가 없어, 의미를 부여하는 대신
관측된 리터럴로 취급한다.

### 3.2 태그 표

| 태그 | 타입 | 페이로드 | 근거 |
|---:|---|---|---|
| `0x01` | NULL | 없음 | **규약** |
| `0x02` | INT32 | int32 LE | **규약** |
| `0x03` | BOOLEAN | 1바이트 (0/1) | **규약** |
| `0x04` | STRING | uint16 LE 문자수 + UTF-16LE | **관측** |
| `0x05` | STRING[] | uint32 LE 개수 + STRING * n | **규약** |
| `0x06` | RECORD | `record_body` | **규약** |
| `0x07` | RECORD[] | uint32 LE 개수 + RECORD * n | **규약** |

`0x05` 를 문자열 배열에 배정한 이유는 전문 8바이트 중 `05` 가 등장하기 때문이나,
그 `05` 가 배열 태그라는 근거는 없다. 임의 배정이다.

### 3.3 NULL 문자열

문자열 값이 `None` 인 경우 `0x01`(NULL)을 쓴다. 길이 0인 문자열(`""`)과 구분한다.

## 4. 검증되는 것과 검증되지 않는 것

`python3 -m syneai.wmvalues --self-test` 가 확인하는 것:

| 검사 | 내용 |
|---|---|
| `prefix_matches_sample` | 최상위 레코드를 `com.wm.data.ISMemDataImpl` 로 인코딩했을 때 선두 33바이트가 관측 표본과 **정확히 일치** |
| `roundtrip_bytes` | encode → decode → encode 결과가 바이트 단위로 동일 |
| `roundtrip_values` | encode → decode 결과가 원본 값과 동일 (중첩·배열·NULL 포함) |
| `base64_stable` | base64 왕복이 안정적 |

검증되지 **않는** 것: 실제 webMethods Integration Server 가 이 바이트열을
읽을 수 있는지. 3.2 태그 표가 틀렸다면 읽지 못한다.

## 5. 실제 표본이 생겼을 때

```sh
python3 -m syneai.wmvalues --verify <node.ndf 또는 base64 텍스트 파일>
```

이 명령은 파일에서 `IRTNODE_PROPERTY` 값을 찾아 디코딩을 시도하고, 성공하면
재인코딩해 원본과 바이트 비교한다. 세 가지 결과가 나온다.

- **왕복 일치** — 3장 규약이 실제 포맷과 맞다. 문서의 "규약" 표기를 "관측"으로 올린다.
- **디코딩 실패** — 태그 표가 틀렸다. 실패 지점의 바이트 오프셋과 문제의 태그를 보고한다.
- **왕복 불일치** — 디코딩은 되나 인코딩이 다르다. 차이 위치를 보고한다.

태그 표는 `wmvalues.py` 의 `TAGS` 딕셔너리 한 곳에만 있다. 실제 포맷이 밝혀지면
그 딕셔너리와 `PREAMBLE` 만 고치면 되고, 나머지 생성기는 손대지 않아도 된다.

## 6. 이 선택이 코퍼스에 미치는 영향

`PLAN-EAI.md` 원칙 6은 "바이너리 블롭을 회피하지 않는다"이다. 평문 XML로
대체하면 엔진이 실전에서 마주칠 가장 큰 장벽이 사라지기 때문이다.

규약 기반 인코딩은 그 원칙을 **부분적으로** 지킨다.

| 재현되는 것 | 재현되지 않는 것 |
|---|---|
| 테이블·컬럼 바인딩이 XML 텍스트에 없고 base64 블롭 안에만 있다는 구조 | 실제 webMethods 바이트 시퀀스 |
| 블롭을 디코딩해야 `update.expression` 의 DB측 함수 변환을 찾을 수 있다는 성질 | 실제 태그 값 |
| UTF-16LE·리틀엔디안 길이 필드 등 관측된 인코딩 특성 | 배열/레코드 표현 |

엔진 입장에서 "블롭을 디코딩하는 코드를 작성해야 한다"는 요구는 동일하게 발생하고,
포맷이 확정되면 디코더의 태그 표만 교체하면 된다. 대신 이 코퍼스를 통과한 디코더가
실제 운영 블롭도 읽는다는 보장은 없다 — 그 보장은 실제 표본으로만 얻을 수 있다.
